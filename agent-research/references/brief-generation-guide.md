# Brief 生成指南

## 核心原则

Brief 是整个流程的质量天花板。一份好的 Brief 不是"帮我搜 X"，而是一份让任何 capable agent 都能高效执行的研究任务书。

**1. 第一人称研究者视角** — 像专家请教专家。用"我正在研究..."开头，而不是"请搜索..."。

**2. 已有信息自然融入叙述** — WebSearch 已获取的信息作为背景自然出现，展示已做功课。
- ❌ "已知：Turborepo 支持缓存。仍需补充：缓存细节。"
- ✅ "通过官方文档了解到 Turborepo 使用 content-addressable storage 做本地缓存，但文档没有讲透自建 Remote Cache 的实际方案..."

**3. 缺口转化为有深度的具体问题** — 问题本身体现研究者的理解水平。
- ❌ "需要了解缓存机制的详细说明"
- ✅ "在 100+ packages 的 monorepo 中，缓存命中率实际表现如何？有哪些常见的缓存失效陷阱？"

**4. 背景足够但不冗余** — 给足"为什么研究"和"已知什么"，去掉内部工具链细节。

**5. 验收标准可检验** — 每条可二元判断，不用"尽量详细"之类模糊要求。
- ❌ "请提供详细信息"  ✅ "至少列出 2 个方案并比较稳定性和维护活跃度"

**6. 输出格式要求具体化** — 明确答案结构、支撑信息（来源链接、版本号、日期）、总长度。

## 反面示例

```
❌ 机械填充 Brief：

# 研究任务：Turborepo 缓存

## 已知信息
Turborepo 是一个构建工具，支持本地缓存和远程缓存。

## 仍需补充
- 缓存机制的详细说明
- 常见问题

## 期望输出
请提供详细信息。
```

**问题清单：**
- "已知信息/仍需补充" 是机械化的模板句式
- "缓存机制的详细说明" 毫无深度，像搜索引擎的关键词
- "请提供详细信息" 没有任何指导性
- 没有验收标准 — 无法判断研究何时完成
- 没有上下文 — Agent 不知道这个研究用来干什么

## 正面示例

### 示例 A：有前置信息的深度研究（WebSearch 已获取官方文档）

```
# Turborepo 缓存体系深度研究

我正在系统梳理 Turborepo 的缓存机制。通过官方文档已经了解到它使用
content-addressable storage 做本地缓存（存储在 node_modules/.cache/turbo），
并支持通过 Remote Cache 连接 Vercel 实现团队共享。

但有几个在实际大规模使用中很关键的问题，文档没有讲透：

1. **自建 Remote Cache**：不依赖 Vercel 的情况下，社区有哪些成熟的
   自建方案？（如 turborepo-remote-cache、ducktape）它们各自的稳定性、
   维护活跃度、已知限制是什么？

2. **大规模场景的缓存表现**：在 100+ packages 的 monorepo 中，
   缓存命中率实际表现如何？有哪些常见的缓存失效陷阱
   （比如环境变量变化、隐式依赖未声明）？

3. **与 Nx 的缓存对比**：两者在缓存粒度（task-level vs file-level）、
   远程缓存架构、增量构建策略上的核心 trade-off 是什么？

请为每个问题提供：
- 结论（2-3 句总结）
- 支撑来源（链接 + 简述可信度）
- 如果有实际项目案例，优先引用

验收标准：
- [ ] 至少列出 2 个自建 Remote Cache 方案并比较
- [ ] 包含真实项目的缓存命中率数据或经验
- [ ] Nx 对比覆盖缓存粒度和远程缓存两个维度
```

**为什么这是好 Brief：** 第一人称开头，已有知识自然融入背景，3 个问题都很具体且有深度，输出格式和验收标准都可操作。

### 示例 B：几乎没有前置信息的研究（WebSearch 仅找到官方概览）

```
# Angular Signals 迁移实践研究

我们的项目正在评估从 Angular 传统的 Zone.js + 脏检查迁移到
Signals-based reactivity 的可行性。项目规模约 300 个组件，
大量使用 RxJS，有自定义的状态管理层。

我需要理解：

1. **迁移路径**：官方推荐的渐进式迁移策略是什么？是否可以
   Zone.js 和 Signals 共存？共存期间有哪些已知的性能陷阱或行为不一致？

2. **RxJS 互操作**：toSignal() / toObservable() 在实际使用中的
   边界情况 — 内存泄漏风险、错误传播行为、与 async pipe 的交互。
   特别关注：在 OnPush 组件中混用 Signal 和 Observable 是否有坑。

3. **社区踩坑经验**：中大型项目（50+ 组件）实际迁移过的团队，
   他们遇到了什么问题？回滚过吗？最终收益（包大小、首屏性能、
   开发体验）是否符合预期？

输出格式：
- 每个问题独立回答，结论在前，细节在后
- 引用的经验帖/文章需标注日期（2025 年之前的可能已过时）
- 如果有代码片段展示迁移模式，标注 Angular 版本号

验收标准：
- [ ] 迁移路径部分引用了 Angular 官方文档或 RFC
- [ ] RxJS 互操作至少覆盖 toSignal() 的 3 个边界情况
- [ ] 包含至少 1 个真实项目的迁移经验（非官方 demo）
```

**为什么这是好 Brief：** 给足了项目背景（规模、技术栈），让 Agent 知道答案需要考虑什么约束。问题有深度（不是"介绍 Signals"而是"OnPush 中混用的坑"）。

### 示例 C：多 Brief 并行（同时研究官方生态和社区迁移）

```
---
📋 Brief 1/2：Deno 2.0 官方生态与核心机制
---

我正在为 Deno 2.0 建立系统性的知识库。通过官方博客了解到 2.0
的核心变化是"backwards compatible with Node.js and npm"，
但需要深入理解其实现机制。

研究问题：
1. Node.js 兼容层的实现原理 — 是 polyfill、转译还是原生支持？
   哪些 Node API 仍然不兼容？
2. npm 包的加载机制 — node_modules 回归后，Deno 的模块解析
   策略是什么？和 Node.js 的 resolve 算法有何区别？
3. 权限模型在 2.0 中的变化 — 引入 npm 包后，权限粒度如何
   控制第三方包的系统访问？

输出格式：每个问题提供结论 + 技术细节 + 来源链接
验收标准：
- [ ] Node 兼容层有架构层面的解释（不只是"支持 Node API"）
- [ ] 模块解析区别有具体的技术对比
- [ ] 权限模型变化有配置示例

---
📋 Brief 2/2：Node.js → Deno 2.0 社区迁移实战
---

基于 Deno 2.0 号称兼容 Node.js，我需要了解社区实际的迁移体验。

研究问题：
1. 真实项目迁移案例 — 有哪些中型以上项目（非 demo）完成了
   从 Node.js 到 Deno 2.0 的迁移？过程中最大的阻碍是什么？
2. 工具链兼容性 — Webpack/Vite/ESBuild 等构建工具在 Deno 2.0
   下的可用性如何？哪些需要替代方案？
3. 生产环境部署 — Docker 镜像大小对比、冷启动性能、
   与云平台（Vercel/Fly.io/Railway）的集成成熟度。

输出格式：案例需标注项目规模和迁移日期
验收标准：
- [ ] 至少 2 个真实迁移案例（有仓库链接或博客链接）
- [ ] 构建工具兼容性覆盖 Vite 和 ESBuild
- [ ] 至少 1 个生产部署的性能数据
```

**为什么这是好拆分：** 两个 Brief 完全独立 — Brief 1 聚焦官方技术机制，Brief 2 聚焦社区实战。可以同时发给不同 Agent。

### 示例 D：补充 Brief（首轮验收发现缺少生产部署细节）

```
# 补充研究：Turborepo 自建 Remote Cache 生产部署

上一轮研究已经确认 turborepo-remote-cache 是社区主流的自建方案，
了解了基本架构（S3 + Express server）和开发环境配置。
但生产环境的两个关键问题仍然缺失：

1. **认证与安全**：生产环境中如何配置 token 认证？是否支持
   team-scoped 的缓存隔离（不同团队只能访问自己的缓存）？
   有没有现成的 RBAC 方案？

2. **存储成本控制**：大型 monorepo（日均 500+ 构建）的缓存体积
   增长速度大约是多少？有哪些 TTL 或 LRU 清理策略？
   S3 lifecycle rules 还是应用层清理更合适？

只需补充这两点，不要重复上一轮已有的内容。

验收标准：
- [ ] 认证配置有具体的配置示例或文档链接
- [ ] 缓存清理策略至少覆盖 TTL 和存储上限两种方式
```

**为什么这是好补充 Brief：** 明确引用了上一轮结果作为上下文，只聚焦缺失项，验收标准精准。

## 结构检查清单

每个 Brief 写完后，快速自查：

- [ ] 有背景与动机（为什么研究）
- [ ] 研究问题是具体的问题，不是关键词或模糊需求
- [ ] 有范围约束（聚焦/排除/时效）
- [ ] 有期望输出格式（怎么组织答案）
- [ ] 有可检验的验收标准（每条能二元判断）
- [ ] 读起来像专家请教专家，而不是机器填表

## 复杂度判断

| 信号 | Brief 数量 | 拆分维度 |
|------|-----------|---------|
| 单一明确问题 | 1 | — |
| 需要多种来源类型（文档 + 社区 + 实时） | 2-3 | 按信息类型 |
| 跨多个独立子主题 | 2-3 | 按子主题 |
| 同一主题的不同深度 | 1（一个 Brief 覆盖） | — |

拆分原则：每个 Brief 独立可执行，不依赖其他 Brief 的结果。
